# How we are going to test the whole product

**Written 2026-09-04, before anything runs.** Everything is deployed to
`https://panel.cartze.shop` (HTTPS live). This is the plan; the findings go in
`2026-09-04-full-run.md` beside it.

---

## The one rule this plan is built on

**Every layer of testing is blind to something, and the blind spots are what
ship.** So the plan is not "run the tests" — it is *seven layers, each chosen
for what the layer above it cannot see*, plus the one thing no automation can
do, which is a person holding the shop.

| Layer | Sees | **Cannot see** |
|---|---|---|
| 1 · Scanners | code shape: dead routes, rules written twice, untested absences | anything about behaviour |
| 2 · Backend suite | every rule, every refusal, 2,430 tests | the browser; and by default **SQLite, not MySQL** |
| 3 · Panel units | logic, gating, 128 files | layout — jsdom has **no layout engine** |
| 4 · QA sweep | the product driven **from outside**, 21 phases, as a real shop | pixels; anything the API cannot reach |
| 5 · Playwright | layout at 4 widths, 11 projects, 21 specs | anything not *at rest* — a wrapped button is "fine" |
| 6 · Live smoke | that the deployed thing is the built thing | correctness (read-only, no writes) |
| 7 · **You, by hand** | everything above missed | — |

Layers 1–5 run **locally**. Layer 6 is read-only against live.
**Nothing destructive touches the live box** — the sweep creates and mutates
shops, so it never points at production. Any write on live, I ask first.

## Order, and why it is that order

Cheapest and widest first, so a broken foundation is found before an hour of
browser time is spent on it.

### 0 · Ground truth (≈2 min)
Migrations current, local API healthy, **and the backend suite forced onto
MySQL**. `phpunit.xml` pins `sqlite/:memory:`, so a plain run tests a database
production does not use — a green run against SQLite has already been reported
here as if it meant MySQL, and it did not. Fresh `shopos_test`, strict mode, UTC.
The demo `shopos` database is never touched.

### 1 · Scanners (≈1 min) — 9 of them
```
backend/scripts/  dead-endpoints · dead-rules · one-rule-many-paths
                  rule-lives-in-one-place · silent-nulls · untested-absence
                  clock-dependent-tests
docs/qa/          unreachable-pages · screen-permission-drift
```
These find the class of bug tests cannot: a rule stated in a comment and
implemented nowhere, an endpoint no screen calls, a page no menu reaches.

### 2 · Backend suite on MySQL (≈3 min) — 2,430 tests
Exit code and JUnit XML, not the printed summary. The summary has lied here
before: `artisan test` once printed "2225 passed" while exiting 1.

### 3 · Panel units (≈30 s) — 128 files, 1,487 tests

### 4 · The QA sweep, A→U (≈25 min) — the main event
21 phases that drive the product from outside as a real shop would, in the
order a shop actually does things:

| | |
|---|---|
| A | the platform console before any shop exists |
| B | what each of the 8 trades is actually given |
| C | selling — and whether the money and the shelf agree afterwards |
| D | the shelf away from the till (receive, count, adjust, dispose) |
| E | money that is not a sale |
| F | **the seams** — where two modules meet |
| G | what only one trade has |
| H | the till with **no server** |
| I | who is standing at the counter, on which lane |
| J | the Expense Manager ↔ drawer wire |
| K | more than one shop under one roof |
| L | the floor — dine-in, KOT, settle |
| M | money the shop gives away on purpose (points, coupons, promos) |
| N | sales that are not a sale yet, and ones that go backwards |
| O | quotations and advances |
| P | the **day** across every lane |
| Q | paper, tanker, workshop |
| R | **the customer** — signed out, then as a customer |
| S | the shelf that ages (batches, expiry) |
| T | who changed what (audit) |
| U | the same thing in three sizes |

### 5 · Playwright (≈45 min) — 11 projects × 21 specs
Four widths (phone / tablet portrait / tablet landscape / desktop), the
restaurant at three sizes, six trades, and the storefront **signed out**.

### 6 · Live smoke, read-only (≈2 min)
Health, HTTPS, the deployed bundle carries the newest work, `APP_NAME`, and the
storefront renders to a stranger.

## The edge cases I will deliberately go looking for

Automation proves the paths it was written for. These are the ones that
historically break in this product, and each gets asked on purpose:

**Money**
- a bill with no exact cash tender (sub-rupee), and cash rounding at 0/1/5/10
- a discount larger than the line · a discount at exactly the ceiling
- a refund of a sale that used points **and** a coupon **and** a trade-in
- Rs → litres at a rate that does not divide evenly *(new today)*
- an amount too small to buy 0.001 of anything *(new today)*

**Stock**
- selling the last unit twice, from two lanes, at the same moment
- a size that has run out while the parent has stock
- a pack sold while the base unit is short
- a dip **outside** the calibration chart *(new today)*

**Time**
- the 3rd of the month, month-end, and `period=monthly` on the 1st
- a shift that spans midnight · a day left open overnight
- Karachi vs UTC — `toISOString().slice(0,10)` is yesterday before 05:00

**Absence** (the class that has produced the most live defects here)
- an optional field left out where the column has a default
- a customer with no phone · a product with no cost · a tank with no chart
- a shop with a module **off** reaching a screen the menu no longer shows

**Offline**
- sell, reload the tab, keep selling, come back online
- two tills, same shop, same product, both offline
- a rate that changed while the till was down *(new today — the amount wins)*

**Permission**
- every screen asked as: owner · manager · cashier · waiter · kitchen · finance
- a **read** gated behind a `*.manage` permission (a known bug class here)

## How a finding is recorded

Every issue goes in the run log immediately, with:

| # | Where | What | Severity | State |
|---|---|---|---|---|

- **State** is `reproduced`, `suspected`, or `mine` — a harness bug is written
  down too, because three of the last four "bugs" were the guard, not the code.
- **Severity**: `blocker` (money or stock is wrong) · `major` (a shop cannot do
  the job) · `minor` (it works, it is ugly or slow).
- A count of findings is meaningless without a count of attempts, so each
  section records **what was asked**, not only what failed.

## What this plan does NOT cover, and I will not pretend it does

- **The mobile app** — excluded by you; it is Phase 0 and has no gates at all.
- **iOS Safari** — cannot be run on this machine. Playwright's WebKit is a
  modern build; an old iPad is not reproducible here.
- **Load / concurrency at scale** — the sweep runs two lanes, not two hundred.
- **The live database.** I test the product, not your production data.
