# Full-product QA run — 2026-09-04

Everything is deployed to `https://panel.cartze.shop` (HTTPS live, http redirects).
This run tests the product **end to end**, and every issue found is written down
here as it is found — including the ones that turn out to be my own harness.

## Rules for this run

1. **Nothing destructive touches the live box.** The sweep builds and mutates
   tenants; it runs against local. Live gets read-only checks only, and any
   write on live is asked about first.
2. **A finding is not a bug until it is reproduced.** Each row says which.
3. **A count of findings is not evidence without a count of attempts.** Every
   section records what was asked, not just what failed.

### Step 4 — the QA sweep, A→U

**First run: 1790 ok, 23 BUG, 13 QUERY.**

All 23 were checked one at a time. **None of them is a product bug.** Every one
is the sweep asking a trade for a module that trade is not given — and the
product refusing correctly.

| Group | Trades | Module they lack |
|---|---|---|
| gross profit ≠ revenue − cogs | all 8 | — see below |
| start a layaway → 403 | food, food_restaurant, mart, petroleum, pharmacy | `documents` |
| the coupon list → 422 | food, food_restaurant, automotive, petroleum, pharmacy, services | `promotions` |
| the claims list → 403 | automotive, petroleum, food_restaurant | `disposals` |
| draw a count sheet → 403 | food_restaurant | `stocktake` |

**The denominator, checked before concluding anything:** the trades that HAVE
each module pass the same check under different wording —
`retail · layaway opened with its down payment`, `mart · one-use coupon
redeemed once`, `mart · count applied · shelf now 7`, `pharmacy · the bin and
the claim stay apart`. My first grep used the failure's wording and found no
passes, which looked far worse than it was. **The check was the fix.**

**The gross-profit one is different and worth reading.** The report is right and
the sweep was old:

```
revenue     GROSS — a refunded sale still brought its money in
refunds     its own line, beside the revenue it reduces
gross_profit = (revenue − refunds) − cogs
```

The sweep asserted `revenue − cogs`, so it reported a bug on all eight trades,
each off by **exactly the 500 the sweep itself had refunded a few checks
earlier**. `ReportService::summary` explains the design in a comment; the sweep
had never been updated to match.

#### The finding underneath all 23

**The sweep was written when every module was on for every shop, and was never
updated for the module-gating change.** It then produced 23 false bugs — which
is worse than no sweep, because a harness that cries wolf 23 times teaches you
to ignore the 24th.

#### What was done about it — refusal as the check, not a skip

Skipping would have left the fence untested, and the fence is exactly what a
shop owner asks about: *"a module I was not given had better not show
anywhere."* So `api.gated_on()` was added: a shop **without** the module must be
**refused with 403**, a 200 is reported as a **MODULE LEAK**, and anything else
is a fence that throws instead of refusing.

**Second run: 1795 ok, 0 BUG, 0 QUERY** — and, importantly, **31 module-fence
refusals are now checked that were checked by nothing before**, while every
trade that has the module still does the work.

#### Mutation — proving the new guard can fail

`feature:promotions` removed from the coupon routes:

```
✘ BUG M automotive     · MODULE LEAK — the coupon list without `promotions`
✘ BUG M food           · MODULE LEAK — …
✘ BUG M food_restaurant· MODULE LEAK — …
✘ BUG M petroleum      · MODULE LEAK — …
✘ BUG M pharmacy       · MODULE LEAK — …
✘ BUG M services       · MODULE LEAK — …
```

Restored and verified byte-identical to the committed file.

### Step 5 — Playwright

**Batch 1 (phone + tablet-portrait), first attempt: 150 passed, 2 failed.**

Both failures were `selling.spec · a cash sale rung on the till reaches the
server`, and neither was about the product. They took two rounds to understand
and each round is worth keeping:

**Round one — "the till listed no sellable shelf items", `Received: 1`.**
Reproducible, never flaky, always exactly one. The catalogue API was asked
directly and returned **13 shelf items, every one `sold_out: false` with 240 in
stock**. The page snapshot Playwright saved showed the till had rendered exactly
one of them.

The cause is in `auth.setup`: the browser suite signs in as
**`sweep-mart@qa.test` — the QA sweep's own shop.** The sweep had just added a
dozen `Sweep …` products to it, the till renders a screenful rather than the
whole catalogue, and the shelf's items fell off it. **Two suites, one shop, and
the first to run changes what the second sees.**

`fillCart` already carried a comment about this exact disease one level down:
*"a suite whose result depends on which project ran first is not measuring the
product."* It came back one level up — which SUITE ran first.

**Round two — the fix exposed a second bug.** With the search in, the spec hung
for its full five minutes on `.nth(1)`. `commitProduct` calls `setSearch("")`
after every add — correctly, because a cashier scanning a queue should not have
to clear the box — so the first click threw the grid back to page one, where the
second shelf item was not. Now the fixture searches **once per item**, which is
also what a cashier does. 5 minutes → 8.3 seconds.

**Batch 1, after both fixes: 152 passed, 0 failed, 26 skipped by project.**

**Batches 2–4:** desktop + tablet-landscape **165 passed**, restaurant ×3 +
storefront ×2 **35 passed**, the six trade projects **23 passed**.

**Playwright total: 375 passed, 0 failed, across all 11 projects.**

### Step 6 — live smoke (read-only) — and the one real bug in this run

| | |
|---|---|
| HTTPS | live; `http://` redirects to it |
| service worker + manifest | both 200 — the offline shell can register |
| storefront to a stranger | 200 |
| API health | ok |
| `APP_NAME` | still reports `ShopOS`, not CartZe — server `.env`, unchanged |

And then the finding this whole run is worth having had:

```
GET https://cartze.shop/api/v1/products   (no Accept header)   → 500
GET https://cartze.shop/api/v1/sales      (no Accept header)   → 500
GET .../products  Accept: application/json                     → 401 ✅
```

Reproduced locally at once, and the cause was `Route [login] not defined` —
Laravel redirecting a guest to a login route an API-only app does not have.

**Why nothing had caught it:** every test in the suite used `getJson()`, which
sets the header. The bug lives in the half of the world that does not.

Fixed in `bootstrap/app.php` (`redirectGuestsTo` returns null for `api/*`, so
the middleware throws and the existing 401 renderable answers), and guarded by
`UnauthenticatedIsRefusedTest` — which sends **no Accept header on purpose**,
across four doors of different shapes.

**Mutation, and my first one was wrong.** Replacing the closure with a literal
`'/login'` string did NOT fail the test — a string path redirects rather than
throwing, so it was not the bug. Removing the fix entirely is:

```
✘ /api/v1/products     answered 500 to a request with no Accept header
✘ /api/v1/sales        answered 500 …
✘ /api/v1/fuel/tanks   answered 500 …
✘ /api/v1/admin/tenants answered 500 …
✘ an expired or invented token …  Failed asserting that 500 is identical to 401
✘ the refusal says so in the api envelope
```

Backend after the fix: **2524 tests, 0 failures** (MySQL 9.7, UTC, strict).

### The two product findings, both fixed and both guarded

1. **Every API route answered 500 instead of 401** to an unauthenticated
   request that did not send `Accept: application/json` — on live. The panel
   always sends it, so no shop had hit it; everything else does.
2. **`GET /admin/staff/{staff}`** was reachable and called by nothing. Removed.

### What the run cost to trust

Seven of nine findings were the test estate, not the product, and that is the
uncomfortable half of this report:

* **three of nine scanners had not been running on this machine at all** —
  two crashed on the previous machine's folder names, one read zero files.
  A third of the static safety net was decorative.
* **the sweep had not been updated for the module-gating change** and produced
  23 false bugs across all 8 trades. A harness that cries wolf 23 times is
  worse than no harness.
* **the browser suite and the sweep share one shop**, so the first to run
  changed what the second saw — which produced a red `selling.spec` that had
  nothing to do with selling.

None of them passed silently. Every one refused, crashed, or reported — which
is the design working. But *"the tests are green"* meant less on this machine
than it looked, and it means more now.

### What did NOT find anything

Worth recording, because a clean result is only evidence if the question was
asked: the backend suite (2,524 on MySQL), the panel units (1,487), Playwright
(375 across 11 projects), and six of the nine scanners each ran and found
nothing. The sweep's second run asked 1,795 questions of eight trades and found
nothing.
