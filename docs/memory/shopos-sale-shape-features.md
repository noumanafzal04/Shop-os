**3 "sale-shape" vertical features shipped 2026-07-22 (471 backend tests green + web build clean).** User picked "3 sale fixes then Offline" — did these first because Offline POS will serialize/queue the sale + stock contract, so changing it after offline = rework. See [[shopos-audit-backlog]], [[shopos-offline-plan]].

**1. Prescription (Rx) capture — pharmacy.** Was warn-only; now RECORDED on the sale. Migration `2026_07_22_000002_add_prescription_to_sales` adds nullable `prescription_number, prescriber_name, patient_name, prescription_notes` to `sales`. `StoreSaleRequest` accepts them (all nullable — NEVER hard-blocks a sale). `CreateSaleAction` persists them. Invoice blade shows an ℞ line. Sales serialize via the model (no SaleResource) so fields appear automatically. POS (`PosPage`): `CartLine.requires_prescription`; `cartHasRx = cart.some(...)`; a warning-styled "Prescription details" panel (Rx#, patient, prescriber) shows above payment when the cart holds an Rx item; sent in checkout. Tests: `PrescriptionCaptureTest` (recorded / optional).

**2. Variant-medicine FEFO + expiry fence.** Batches were product-level only (`$batchScope = $variant === null`), so variant meds skipped FEFO + the expiry block. FIX: migration `2026_07_22_000003_add_variant_to_product_batches` adds nullable `variant_id` FK to `product_batches`. `InventoryService`: `$batchScope` no longer requires `variant===null`; added `$scopeVariant` closure (`variant_id` NULL → `whereNull`, else `where`) applied to the expiry-fence, FEFO-depletion, and restore queries — so lots are scoped to the exact target (product-level vs a specific variant). `ProductBatch` got a `variant()` relation. `BatchController::store` accepts+validates `variant_id` (must belong to product) and passes it to `adjust`; `destroy` passes `variant_id`. `ReceivePurchaseOrderAction` now creates variant-scoped lots (removed the `variant_id === null` guard). Tests in `BusinessEdgeCasesTest`: per-variant FEFO + expired-variant fence. Product-level behaviour unchanged (NULL variant_id = old path).

**3. Sell-on-credit (khata) — all verticals.** Migration `2026_07_22_000004_add_customer_credit`: `customers.credit_balance` (owed) + `credit_limit` (nullable cap); new append-only `customer_ledger_entries` (type charge|payment|adjustment, amount, balance_after, method, sale_id, note, created_by). `PaymentMethod::Credit`. `CustomerLedgerEntry` model extends `Model` directly (NOT BaseModel — like SalePayment/StockMovement; append-only, no soft-deletes/updated_by — that was a bug: BaseModel needs updated_by+deleted_at cols). `Customer`: casts + `ledgerEntries()` + `chargeCredit()` (enforces credit_limit → `CREDIT_LIMIT_EXCEEDED`) + `recordCreditPayment()`. Credit is a TENDER: `CreateSaleAction` sums `credit` tenders → `chargeCredit` (needs a linked customer, else `CREDIT_REQUIRES_CUSTOMER`; whole txn rolls back on limit). So amountPaid = total (credit counts as tendered), change=0; cash reconciliation ignores credit (reads method='cash' rows). `StoreSaleRequest` allows `credit` in payment_method + payments.*.method. Repayment: `POST /customers/{id}/payments` (`RecordCustomerPaymentRequest` cash/card/bank_transfer/other) → `recordCreditPayment`; customer `show` now appends `ledger` (last 50). `credit_limit` added to Store/UpdateCustomerRequest. POS: `credit` method button (grid-cols-4 cash/card/credit/split) — full-credit needs a customer (`creditNeedsCustomer` blocks checkout + note); split tender dropdown has "Credit (khata)"; Charge button → "On credit · Rs X". Customers page: editor has credit_limit field; detail modal has a khata card (balance owed / limit, record-payment amount+method, ledger statement); `customersService.recordPayment` + `useCustomerMutations().recordPayment`. Tests: `CreditSaleTest` (full/split/no-customer/limit/repayment).
